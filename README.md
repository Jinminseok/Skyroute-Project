# ✈️ SkyRoute

> 항공권 예매부터 운항 관리, 체크인·탑승까지 하나로 연결한 항공사 통합 웹 서비스

---

## 📌 프로젝트 소개

**SkyRoute**는 실제 항공사의 운영 업무 흐름을 반영한 **항공권 예매 및 운항 관리 시스템**입니다.
사용자(USER) · 지상직(STAFF) · 관리자(ADMIN) 세 가지 역할을 분리하고, 각 역할의 업무가 하나의 데이터 흐름으로 이어지도록 설계했습니다.

| 항목 | 내용 |
| --- | --- |
| 개발 기간 | 2026.06.10 ~ 2026.07.28 (약 7주) |
| 개발 인원 | 5명 |
| 소속 | 쌍용강북교육센터 AWS & CI/CD 기반 Java 클라우드 Full-Stack 개발자 양성과정 파이널 프로젝트 2조 |
| 기획 배경 | 실제 항공사의 운영 업무를 반영한 실무형 항공 예매 및 운항 관리 시스템의 필요성 |

### 🔄 서비스 업무 흐름

1. **관리자** — 공항 권역, 게이트 구역, 노선 유형, 항공기, 운임 시즌, 환불 정책 등 최상위 기준 정보 등록
2. **지상직** — 공항·게이트·노선·좌석·운임 등 운영 데이터 등록 후 운항 스케줄 등록
3. **사용자** — 항공권 검색 → 탑승객 정보 입력 → 좌석 선택 → 결제 → 예약 확정
4. **지상직** — 예약 확정 승객 체크인 → 탑승 확정 / 노쇼 처리
5. **예외 흐름** — 지연·결항 발생 시 안내 등록 및 운항 상태 변경, 사용자 예약 취소 시 정책 기반 자동 환불

## 💡 핵심 구현

**1. DB 인덱스로 좌석 중복 예약 방지**
- 애플리케이션 락(`synchronized`, `SELECT ... FOR UPDATE`) 대신 Oracle 함수 기반 유니크 인덱스를 사용해, `HOLDING`·`CONFIRMED` 상태 티켓에만 (항공편, 좌석) 중복을 막았습니다.
- 동시에 같은 좌석을 선택하면 한 요청만 성공하고, 해제(`RELEASED`)된 좌석은 다시 판매할 수 있습니다.
- 별도의 재고 테이블 없이 `전체 좌석 − (확정 + 만료되지 않은 선점)`으로 잔여 좌석을 계산하며, 유아는 좌석을 점유하지 않도록 처리했습니다.

**2. 좌석 임시 선점(HOLD) 10분 + 자동 반납**
- 결제 요청 시 서버에서 좌석 상태를 다시 확인한 뒤 10분간 선점합니다.
- `@Scheduled` 작업이 1분마다 만료된 선점을 해제하고, 좌석 조회 시에도 만료 시각을 함께 확인해 스케줄러가 늦더라도 좌석이 잘못 판매되지 않도록 했습니다.

**3. 결제 서버 검증과 금액 스냅샷**
- 클라이언트 값을 그대로 믿지 않고 PortOne / TossPayments 서버에 결제 내역을 직접 조회해 금액·상태·주문번호를 예약 정보와 대조합니다.
- 결제 실패 처리는 별도 트랜잭션(`REQUIRES_NEW`)으로 분리해, 오류로 롤백되더라도 좌석 반납 기록은 반드시 남도록 했습니다.
- 티켓 금액과 예약 총액은 예약 시점의 값으로 저장해, 이후 운임이 바뀌어도 이미 판매된 예약 금액에는 영향이 없습니다.

**4. 정책 테이블 기반 취소·환불**
- 출발일까지 남은 일수별 수수료율을 `REFUND_POLICY` 테이블로 관리하고, 환불 시 정책을 조회해 금액을 계산합니다.
- 전액 환불은 `REFUNDED`, 수수료 차감 환불은 `PARTIAL_REFUNDED`로 구분해 기록합니다.
- 관리자가 화면에서 수수료율을 바꾸면 코드 수정·재배포 없이 바로 반영됩니다.

**5. 상태값 기반 업무 규칙**
- 각 상태에 허용되는 행위를 함께 정의하고, 허용된 상태 변경만 처리합니다.

| 구분 | 상태 |
| --- | --- |
| 예약 | `PENDING` → `CONFIRMED` / `FAILED`, `CONFIRMED` → `CANCELLED` |
| 결제 | `READY` → `PAID` / `FAILED` / `CANCELLED`, `PAID` → `PARTIAL_REFUNDED` / `REFUNDED` |
| 좌석 선점 | `HOLDING` → `CONFIRMED` / `RELEASED` |
| 체크인·탑승 | `NOT_CHECKED_IN` → `CHECKED_IN` → `BOARDED`, `NOT_CHECKED_IN` → `NO_SHOW` |
| 운항 | `SCHEDULED`, `BOARDING`, `DEPARTED`, `ARRIVED`, `DELAYED`, `CANCELLED`, `COMPLETED` |

- 체크인 대상은 예약 `CONFIRMED`이면서 결제 `PAID`인 승객으로 제한했습니다.
- 지연·결항 안내 등록과 항공편 상태 변경을 하나의 트랜잭션으로 처리해 둘 중 하나만 반영되는 상황을 막았습니다.

**6. 역할 기반 접근 제어**
- `/admin/**`은 ADMIN, `/staff/**`은 STAFF만 접근할 수 있도록 URL 단위로 권한을 분리했습니다.
- 비로그인 사용자는 항공권 검색·상세 조회와 공지 확인까지만 가능하고, 예약 단계부터 로그인이 필요합니다.
- 정지·탈퇴 계정은 로그인을 차단하고, Fetch API 비동기 요청에도 CSRF 토큰을 검증합니다.

## 🗄 데이터베이스 설계

Oracle 기반 약 30개 테이블을 **기준 정보 → 운영 데이터 → 거래 데이터** 계층으로 나누어 설계했습니다.

| 영역 | 테이블 |
| --- | --- |
| 공통 | `MEMBER`, `NOTIFICATION` |
| 관리자 기준 정보 | `REGION`, `GATE_AREA`, `ROUTE_TYPE`, `AIRCRAFT`, `SEASON`, `REFUND_POLICY` |
| 지상직 운영 데이터 | `AIRPORT`, `GATE`, `ROUTE`, `SEAT_CLASS`, `SEAT`, `FARE`, `FLIGHT`, `FLIGHT_FARE`, `FLIGHT_NOTICE` |
| 콘텐츠 | `NOTICE`, `EVENT`, `FAQ` |
| 예약 · 결제 | `BOOKING`, `BOOKING_PASSENGER`, `SAVED_PASSENGER`, `TICKET`, `PAYMENT`, `REFUND` |
| 사용자 부가 | `FAVORITE_ROUTE`, `CHAT_INQUIRY`, `CHAT_MESSAGE` |

- 모든 PK는 `IDENTITY`로 생성하고, 테이블 간 관계는 FK로 참조 무결성을 보장했습니다.
- 상태값, 금액(0 초과), 기간(종료일 ≥ 시작일), 수수료율(0~100) 등 도메인 규칙을 `CHECK` 제약으로 DB 레벨에서 강제했습니다.
- 기준 정보는 `is_active(Y/N)`로 비활성화하고, 운항 스케줄은 soft delete로 이력을 보존합니다.
- 운항 시각은 UTC로 저장하고, 공항별 IANA 타임존(`Asia/Seoul` 등)으로 변환해 표시합니다.
- 환불은 티켓 단위로 `REFUND`에 기록해 다인원 예약의 부분 취소 이력을 추적할 수 있습니다.

## 🔥 트러블슈팅

**1. 항공 도메인 이해를 바탕으로 한 좌석 테이블 리팩토링**
- 문제 : 초기 `SEAT` 테이블에 행/열 컬럼이 따로 있어 불필요한 데이터가 많았고, 좌석 등급별 운임 비율을 유연하게 관리할 구조가 없었습니다.
- 해결 : 좌석 번호(예: `12A`) 중심으로 단순화하고, 좌석 등급을 `SEAT_CLASS` 테이블로 분리해 FK로 연결했습니다. 좌석 배치도는 DB 조회 대신 좌석 번호 규칙으로 화면에서 동적으로 그렸습니다.
- 결과 : 가격 정책이 바뀌어도 테이블 구조 수정 없이 데이터 추가만으로 대응할 수 있게 되었고, 불필요한 데이터가 줄어 정합성이 높아졌습니다.

**2. 스냅샷 패턴으로 마이페이지 조회 오류 해결**
- 문제 : 마이페이지에 저장한 탑승객 정보(`SAVED_PASSENGER`)와 예약 탑승객 정보(`BOOKING_PASSENGER`)가 외래키로 강하게 묶여, 원본을 수정하면 조회 오류와 정합성 문제가 발생했습니다.
- 해결 : 불필요한 외래키를 해제하고, 예매 시점의 탑승객 정보를 독립된 데이터로 저장하는 스냅샷 방식으로 바꿨습니다. 예매 과정의 중복 저장 로직도 함께 정리했습니다.
- 결과 : 원본 데이터와 예약 당시 데이터의 경계가 분명해져 조회 오류의 원인을 차단했습니다.

**3. 하드코딩된 환불 규정을 DB 정책 테이블로 분리**
- 문제 : 출발 D-Day 기준 환불 수수료 계산이 코드 안의 `if-else`로 작성되어, 정책이 바뀔 때마다 소스 수정과 재배포가 필요했습니다.
- 해결 : `REFUND_POLICY` 테이블을 만들고, D-Day 계산 후 해당 구간의 정책을 조회해 수수료를 계산하도록 바꿨습니다.
- 결과 : 서버를 멈추지 않고 관리자 화면에서 정책을 수정할 수 있는 구조가 되었습니다.
